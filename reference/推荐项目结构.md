建议做成 \*\*monorepo + 单一前端入口 + Tauri 原生层隔离 + Runtime 适配层\*\*。你的方案里已经明确：Android Service 只负责保活、WebSocket、通知、ACK，不负责本地业务存储；消息中心数据由前端业务层打开或恢复时同步到 `StorageRuntime`。所以目录也应该围绕这个原则设计，避免 Android 原生层和前端业务层混在一起。



Tauri 官方推荐结构本身就是“前端项目 + `src-tauri/` Rust 项目”的组合，`tauri.conf.json`、`capabilities/`、`icons/`、`src/lib.rs`、`src/main.rs` 都放在 `src-tauri/` 下；其中 `lib.rs` 也是移动端入口相关代码所在处。(\[Tauri]\[1]) Tauri 也支持 `tauri.android.conf.json`、`tauri.ios.conf.json`、`tauri.windows.conf.json` 这类平台配置文件，所以多端差异不应该硬编码到业务代码里。(\[Tauri]\[2])

\## 3. 前端分层规则



\### `features/`



放页面相关的业务 UI 和状态。例如消息中心列表、未读数量、已读按钮、设置页开关等。



```text

features/messages/

├─ components/

│  ├─ MessageList.tsx

│  ├─ MessageItem.tsx

│  └─ EmptyMessage.tsx

├─ hooks/

│  ├─ useMessages.ts

│  └─ useMarkMessageRead.ts

├─ message.store.ts

└─ message.mapper.ts

```



这里可以调用 `MessageService`，但不要直接调用 `IndexedDB`、SQLite、Tauri `invoke`。



\---



\### `services/`



放业务流程编排。



```text

services/

├─ AuthService.ts

├─ MessageService.ts

├─ SyncService.ts

└─ RealtimeService.ts

```



例如：



```ts

export class MessageService {

&#x20; constructor(

&#x20;   private api: MessageApi,

&#x20;   private storage: StorageRuntime,

&#x20; ) {}



&#x20; async syncMessages() {

&#x20;   const lastId = await this.storage.getSyncState('last\_message\_id')

&#x20;   const messages = await this.api.listMessages({ after: lastId })



&#x20;   await this.storage.saveMessages(messages)



&#x20;   if (messages.length > 0) {

&#x20;     await this.storage.setSyncState(

&#x20;       'last\_message\_id',

&#x20;       messages\[messages.length - 1].id,

&#x20;     )

&#x20;   }



&#x20;   return messages

&#x20; }

}

```



`MessageService` 不关心当前是 Web、Android、Windows、iOS，它只依赖 `StorageRuntime`。

放你方案里的四个核心 Runtime 接口：



```text

runtimes/contracts/

├─ AuthRuntime.ts

├─ StorageRuntime.ts

├─ MessageRuntime.ts

├─ NotificationRuntime.ts

└─ index.ts

```



这里是全项目最重要的抽象层。



```text

平台差异只出现在 Runtime 实现里

```

\### `runtimes/web/`



Web 端实现：



```text

runtimes/web/

├─ WebAuthRuntime.ts

├─ WebStorageRuntime.ts

├─ WebMessageRuntime.ts

└─ WebNotificationRuntime.ts

```



职责：



```text

WebAuthRuntime:

&#x20; localStorage / IndexedDB 保存 token



WebStorageRuntime:

&#x20; IndexedDB + localStorage



WebMessageRuntime:

&#x20; 页面打开时维护 WebSocket



WebNotificationRuntime:

&#x20; 可以先做 noop，或者只在网页前台内提示

```



你的方案里 Web 端“不做系统通知、不做后台保活”，所以 `WebNotificationRuntime` 可以先写成轻量实现或空实现。


```text

&#x20; SQLite / Store / FS

&#x20; Android: invoke keepalive plugin start/stop/status

&#x20; 桌面端走 Tauri notification

&#x20; Android 后台普通通知由 Kotlin Service 自己弹

```

这里的 Android native 层只允许做这些事：




\## 9. Runtime 选择方式



推荐在 `createRuntime.ts` 里统一分发：



```ts

export async function createRuntime(): Promise<RuntimeBundle> {

&#x20; if (isTauri()) {

&#x20;   return createTauriRuntime()

&#x20; }



&#x20; return createWebRuntime()

}

```



然后业务层只拿到：



```ts

export interface RuntimeBundle {

&#x20; auth: AuthRuntime

&#x20; storage: StorageRuntime

&#x20; message: MessageRuntime

&#x20; notification: NotificationRuntime

}

```



应用启动流程：



```text

main.tsx

→ initApp()

→ createRuntime()

→ initAuth()

→ MessageService.syncMessages()

→ MessageRuntime.startRealtime()

→ 渲染 App

```



App 恢复流程：



```text

App resume / visibilitychange

→ MessageService.syncMessages()

→ 同步消息中心

```

\## 10. Android 点击通知后的目录归属



Android 点击通知后，建议这样分层：



```text

NotifyHelper.kt:

&#x20; 构造 PendingIntent，带 messageId。



KeepAlivePlugin.kt:

&#x20; 处理 onNewIntent / notification click。



Tauri 前端:

&#x20; 收到启动参数或 resume 事件。



MessageService:

&#x20; syncMessages() 补拉消息。



StorageRuntime:

&#x20; saveMessages() 写入本地。

```



Tauri 移动插件支持 Android `onNewIntent` 生命周期回调，适合处理通知点击或 deep link 这类“Activity 被重新拉起”的场景。(\[Tauri]\[4])

\## 1. 结论



\*\*之前那套结构基本可用，但服务端需要提前调整。\*\*



原来是：



```text

apps/server/src/modules/

├─ auth/

├─ users/

├─ messages/

└─ realtime/

```



建议改成：



```text

apps/server/src/modules/

├─ auth/

├─ users/

├─ messaging/              # 统一消息核心

├─ conversations/          # 会话、成员、未读、置顶等

├─ channels/               # 渠道账号、渠道配置、绑定关系

├─ connectors/             # QQ / 微信 / Telegram 接入实现

├─ delivery/               # 投递、重试、失败、回执

└─ realtime/               # 推送给自己 App 的 WebSocket

```



这样以后接 Telegram、QQ、微信时，不需要改客户端主架构，只需要在服务端新增 connector。

\## 2. 为什么外部平台应该放服务端，而不是放 Tauri 客户端



以 Telegram、QQ 这类平台为例，它们本身就支持服务端接收事件。Telegram Bot API 官方文档说明，机器人接收更新可以用 `getUpdates` 或 webhook，两者互斥；这天然适合服务端处理。(\[Telegram]\[1]) QQ 机器人官方文档也支持通过 Webhook 或 WebSocket 接收事件，事件会推送到开发者服务器，Payload 里有 `op`、`d`、`s`、`t` 等统一结构。(\[QQ开放平台]\[2])



所以你的客户端不应该直接连：



```text

QQ / 微信 / Telegram

```



而应该只连：



```text

你的服务端 /api

你的服务端 /ws

```



外部平台全部由服务端接入：



```text

QQ / 微信 / Telegram

&#x20;       ↓

server connectors

&#x20;       ↓

统一消息库

&#x20;       ↓

server /ws 推送给你的 App

&#x20;       ↓

Tauri / Web / Android / iOS 显示

```

\## 5. 核心思想：统一消息模型



不要让客户端看到这种数据：



```text

TelegramMessage

QQMessage

WeChatMessage

```



客户端应该只看到：



```text

Message

Conversation

Channel

Participant

```



服务端 connector 负责把外部平台消息转换成统一格式。



```ts

export interface NormalizedMessage {

&#x20; id: string



&#x20; channelType: 'app' | 'telegram' | 'qq' | 'wechat'

&#x20; channelAccountId: string



&#x20; externalMessageId?: string

&#x20; externalConversationId?: string

&#x20; externalSenderId?: string



&#x20; conversationId: string

&#x20; senderId: string



&#x20; direction: 'incoming' | 'outgoing'

&#x20; contentType: 'text' | 'image' | 'file' | 'voice' | 'video' | 'system'



&#x20; content: {

&#x20;   text?: string

&#x20;   mediaUrl?: string

&#x20;   fileName?: string

&#x20;   raw?: unknown

&#x20; }



&#x20; status: 'pending' | 'sent' | 'delivered' | 'failed' | 'read'



&#x20; createdAt: number

&#x20; updatedAt: number

}

```



这样你的客户端消息列表不关心消息来自哪里，只需要根据 `channelType` 显示一个来源标识：



```text

Telegram

QQ

微信

本 App

```

\## 6. 入站消息流程



外部平台收到消息时：



```text

用户在 Telegram / QQ / 微信 发消息

→ 平台推送到 server connector

→ connector 校验签名 / token / webhook

→ mapper 转成 NormalizedMessage

→ messaging.service 保存到数据库

→ conversations.service 更新会话最后消息、未读数

→ realtime 推送给已登录的 Tauri/Web/iOS/Android

→ Android Service 收到你服务端 /ws 消息后弹通知并 ACK

→ App 打开后 syncMessages() 补拉完整数据

```



注意，Android Service 仍然不需要知道消息来自 Telegram 还是 QQ。它只需要收到你的服务端统一 payload：



```json

{

&#x20; "type": "message.created",

&#x20; "messageId": "msg\_123",

&#x20; "conversationId": "conv\_456",

&#x20; "title": "Telegram - Alice",

&#x20; "body": "你好",

&#x20; "channelType": "telegram"

}

```

\## 7. 出站消息流程



用户在你的 App 里回复外部消息：



```text

用户在 App 输入消息

→ POST /api/conversations/:id/messages

→ server 先创建 pending 消息

→ delivery.service 创建投递任务

→ connector.registry 找到对应 connector

→ telegram.sender / qq.sender / wechat.sender 发送

→ 成功后记录 externalMessageId

→ 更新状态 sent / failed

→ realtime 通知所有端更新 UI

```



也就是说，客户端发消息时不直接调用 Telegram、QQ、微信 API，而是：



```text

App → 你的服务端 → 对应 connector → 外部平台

```

\## 11. 需要特别注意的平台差异



不同平台不是简单“收发文本”这么统一。比如 QQ 机器人官方发送消息文档里就有主动消息、被动回复、群聊、单聊、频道、私信、频控等差异，部分能力还和权限、场景、时间窗口有关。(\[QQ开放平台]\[3]) 所以不要在客户端写死“所有渠道都能主动发送任意消息”。



建议在服务端定义：



```ts

export interface ChannelCapability {

&#x20; canReceiveMessage: boolean

&#x20; canSendMessage: boolean

&#x20; canSendImage: boolean

&#x20; canSendFile: boolean

&#x20; canRecallMessage: boolean

&#x20; supportsReadReceipt: boolean

&#x20; supportsDeliveryReceipt: boolean

&#x20; requiresReplyWindow: boolean

}

```



然后客户端根据服务端返回的 capability 控制 UI：



```text

能发文本 → 显示输入框

不能主动发消息 → 输入框禁用

只能回复窗口内消息 → 显示剩余可回复时间

不能发图片 → 隐藏图片按钮

```
